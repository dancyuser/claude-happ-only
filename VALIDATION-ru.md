# Подтвержденные проверки и границы защиты

## Ethernet / Wi-Fi для одного сервера Happ — 13 ноября 2026

На существующей Windows 11 x64 с включенным SnowVPN установлены два постоянных физических маршрута к одному серверу Happ: провод основной, Wi-Fi резервный. Профиль Happ не менялся. Настройка сохраняет GUID, шлюз и метрику каждого выхода; WFP-ограничения Desktop/CLI до локального прокси и ограничения ядра Happ до сервера сохранены.

По явному разрешению пользователя Ethernet программно отключен. Windows выбрала Wi-Fi-маршрут; установленное TCP-соединение ядра Happ имело локальный адрес Wi-Fi. Защищенный диагностический curl через HTTP CONNECT получил HTTPS-ответ со страной DE и тем же внешним IP. После теста Ethernet включен обратно, затем подтвержден основной проводной маршрут. Первую ошибку возврата в частном испытательном скрипте исправили (GUID со скобками); повторный прогон подтвердил автоматическое включение адаптера. Этот частный скрипт и локальные журналы в поставку не входят.

Отдельная итоговая проверка подтвердила оба маршрута в ActiveStore/PersistentStore, HTTP CONNECT и SOCKS, совпадение внешнего IP/страны до и после тестового отказа и блокировку прямого выхода, альтернативного локального прокси и обхода при отказе разрешенного прокси. Завершающий Install-Automated Fix с PreserveExistingPolicyOnly: Status OK, Stage Complete, LegacyPreserved, PolicyCreated false, CLI и Desktop Preflight OK. Claude не запускался и не завершался агентом.

Исправлена ложная ошибка диагностики при оставшемся рабочем соединении Happ через резервный Wi-Fi после возврата основного провода. Проверка удаления только проводного маршрута при включенном адаптере дала иной результат (выбор TUN) и не считается доказательством переключения: положительный вывод основан на реальном отключении адаптера.

Фикстуры проверяют переименование/формат GUID, отказ при обоих недоступных выходах, виртуальном/дублирующем интерфейсе и чужом маршруте, идемпотентное создание двух хранилищ и восстановление нескольких сохраненных маршрутов без недопустимого New-NetRoute -PolicyStore PersistentStore. В этих тестах операции ОС подменены; они не заменяют реальное испытание.

Не проверены: перезагрузка, чистая установка на другом ПК, физическое отключение обоих выходов, все типы адаптеров и бесшовное сохранение каждого TCP-сеанса. Этот результат не доказывает универсальную защиту всех произвольных дочерних программ. Личные IP, GUID, SID, конфигурация и журналы не публикуются.

## Отдельный Claude Code CLI — 12 ноября 2026

До изменения стандартный `.local\bin\claude.exe` отсутствовал в установленном WFP-инвентаре; учитывались Desktop и кэш встроенного Code. Добавлены сохраненный CliExecutable, пользовательское автообнаружение стандартного пути и отдельная цель Preflight/launcher.

После подтверждения пользователем закрытия Desktop/CLI выполнен Fix с UAC, резервной копией и сохранением прежней AppID-политики. Итог транзакции OK, новая политика не создавалась. CLI включен в state.Executables, присутствуют все четыре ожидаемых WFP-ключа для его пути. SYSTEM-синхронизация получает этот путь из конфигурации пользователя, не из собственного USERPROFILE.

Отдельный Preflight Target=Cli завершился OK; билет содержит путь CLI и совпадающий SHA256. Защищенный сетевой эксперимент прошел HTTP CONNECT и отрицательные проверки, страна DE. Итоговый Desktop Preflight также прошел. Создан CLI-ярлык, сохранена отдельная Desktop-цель.

Агент CLI и Desktop не запускал. Проверены инвентаризация и фильтры, сетевой эксперимент через тестовый curl и путь Preflight; реальная интерактивная работа CLI после пользовательского запуска отдельно не испытывалась. В фикстурах проверены CLI CheckOnly, разделение билетов Desktop/CLI и отказ при изменении CLI-файла.

## SnowVPN и исправление проверки ярлыка — 6 ноября 2026

Причина сообщения `Code HTTP proxy/settings check failed` на проверенном ПК: настройки Code корректны, но локальный Happ-прокси недоступен. При первом снимке не было процесса Happ/Xray и слушателя на настроенном порту. После ручного подключения Happ only WiFi HTTP-проверка прошла без изменения настроек Code. SnowVPN оставался включен и не заменял Happ.

Исправленный ярлык проверяет настройки Code без сетевого запроса, выполняет защищенный Preflight с возможностью исправления правил TUN, затем повторно проверяет настройки и свежий билет. Сетевые проверки SOCKS/HTTP CONNECT, страны и запрета обхода сохранены в Preflight. `-SettingsOnly` не выдает транспортного или пускового разрешения.

Исправление и текущая поддержка SnowVPN установлены через `Fix -PreserveExistingPolicyOnly` с резервными копиями. Итог: `Status=OK`, `LegacyPreserved`, `PolicyCreated=false`; выбран `SnowVPN Tun V2`, проверка блокирующего правила TUN прошла. Итоговый Preflight: без замечаний, HTTP CONNECT работает, страна DE, IP до/после совпадает, отрицательные проверки прошли. Агент Claude не запускал и не завершал.

Это проверка обновления существующей установки и сети через тестовую программу. Она не доказывает чистую установку, непрерывное переключение VPN или работу всех дочерних программ. Сам Happ в этом прогоне не отключался; отказ прокси для тестовой программы имитировался ограничением доступа.

## Существующая установка Windows 11 — 30 октября 2026

Пользователь выполнил `Install-Automated.ps1 -Mode Fix -PreserveExistingPolicyOnly` и подтвердил UAC. Отчет транзакции и итогового Preflight проверены отдельно.

| Создание новой политики | PolicyCreated=false, InstallIntent=false |
| Откат | Не потребовался; Rollback=NotNeeded |
| Итоговый Preflight | OK, без замечаний |

Локальные адреса, SID, пути пользователя, журналы и резервные копии в репозиторий не включены. Эта таблица является описанием проверенного объема; исходные административные отчеты остаются на компьютере пользователя.

## Покрытие дочерних процессов

Отдельный read-only снимок уже работающих процессов после установки: 17 процессов, один `conhost.exe` без AppID-тега, ошибок чтения нет. Наблюдатель выдал `CoverageGap`. Процессы для этого снимка агент не запускал и не завершал.

Это подтверждает разрыв покрытия тегами в наблюдавшемся дереве. Снимок не доказывает сетевую утечку и не доказывает блокировку соединений этого конкретного conhost. Полная защита всех произвольных потомков не заявляется.

Наблюдатель служит диагностикой. Он не исправляет токены, не гарантирует обнаружение краткоживущих процессов до первого соединения и не заменяет сетевой фильтр.

## Что пока не проверено

- Создание и активация новой AppID-политики установщиком на чистой Windows 11.
- Поведение новой установки после перезагрузки.
- Живой откат после частичного отказа системных операций. 14 сценариев оркестрации проверены с подменой операций ОС.
- Полный охват произвольных дочерних процессов, системных посредников, WSL, VM и удаленного выполнения.

## Отложенные варианты

Sandboxie и собственный драйвер отслеживания процессов обсуждались как возможные направления. По текущему решению пользователя они отложены: ни один из этих механизмов не добавлен в установщик и не требуется для нынешней установки. Доступ к проектам остается в рамках существующей схемы; файловая песочница не вводится.
